# 存储故障后的对账

存储故障锁表示存在尚未排除的写入不确定性。释放空间、数据库 integrity_check 通过、从归档恢复成功，均不能单独解除这个锁。首先保持接收器和 Tunnel 停止，进入匹配发布的维护状态，保存原九卷和故障现场；原始卷、确认记录、去重记录及未知表全部保留。

## 为什么需要两库核对

插件先在回执库 claim 消息，再调用账本 API，最后保存 created 回执。账本成功、回执落盘失败时，回执可能仍为 pending；HTTP 请求结果不明确时为 unknown。claim 仍阻止原消息重写。删除 pending/unknown、重置游标或重新投递旧消息会损坏这层保护。

当前固定账本镜像的实际 transaction schema 没有 client_session_id 字段。插件发送的 clientSessionId 是可信消息键的 SHA-256，但不能据此声称离线账本数据库一定能查到它。没有持久服务端凭证时，不能按金额、备注或相近时间自动认定某笔交易属于某条不确定消息。

## 只读核对入口

从已停止的服务或验证过的恢复候选制作两个一致的离线 SQLite 副本。若原库有 WAL，必须先用 SQLite backup API 在另外的新文件中保存已提交状态，再把新副本规范为 DELETE journal；不要复制主文件后丢弃 WAL，也不要在原卷执行 journal/checkpoint 改写。

在仓库外新建仅当前用户可读的目录，放入 `ledger.sqlite`、`receipts.sqlite` 和 `scope.json`。scope 仅含从实际迁移配置独立核对出的 ownerId、accountId 字符串；不在聊天或 Git 中展示这些值。两个库不得来自不同快照。然后执行：

```text
node scripts/mac/audit-recovery-receipts.mjs <私有离线核对目录>
```

工具只读打开库，要求完整性通过、DELETE journal、无旁挂 WAL/SHM/journal，核验固定用户、日常支出账户和 SGD。created 回执按精确交易 ID（保留 64 位整数）、所有者、账户、未删除状态、支出类型、金额和备注比对；多条回执共用交易、缺失或矛盾字段均列入人工检查。pending/unknown 始终保持不确定。它不验证分类/发生时间，也不覆盖没有回执的账本写入，不能将零异常报告当作完整业务对账或启动许可。

工具前后核对三个输入的文件哈希，报告只在私有目录独占新建，拒绝覆盖；终端只显示计数。报告中的 reference 是消息键的 SHA-256，便于本机将疑点关联到原回执，不含聊天原文或账户 ID。报告也不要提交 Git。

## 人工处理与恢复边界

逐项检查报告，并核对故障窗口内的实际账本增量、确认处理与消息游标。created 差异先区分正常人工编辑、删除与故障造成的不一致；不能把账本强行改成回执内容。对于 pending/unknown，保留 claim 和原状态；没有可独立确认的交易依据时，不自动补写、不自动改为 created、不向微信补发成功。

若需数据恢复，先恢复到全新候选九卷并完整审查；候选不能自动获得生产标签。只要 Mac 已经产生新数据，就不能直接启动旧 Windows 快照。必须停止两端写入，核对完整增量与永久去重/确认状态，制定一份明确选择哪组数据、如何保留新写入的恢复记录。

只读核对工具及正反测试已实现；它自身不会解除维护或故障锁，也不会修改任何数据库。[恢复批次选择](mac-recovery-generations.md) 和 [版本更新](mac-release-updates.md) 已有独立入口与演练；生产版本更新也已执行，不能用它绕过故障对账。

## 审核后解除故障锁

生产已进入匹配维护状态且三个服务全部停止后，使用九卷备份入口保存并恢复验证当前状态，再执行：

```text
node scripts/mac/production-storage-recovery.mjs prepare <只读生产宿主目录> <九卷备份目录>
node scripts/mac/production-storage-recovery.mjs clear <只读生产宿主目录> <同一九卷备份目录> <私有审核JSON>
```

prepare 重新认证整份加密备份，核验当前九卷身份、没有任何运行容器使用这些卷、完整文件树和两库全表与备份一致，才独占生成全部未确认的审核文件。审核绑定本次故障内容、源码/切换/导入身份、备份清单和数据审计哈希。不得由代理为了通过检查自动填写确认。

操作者完成对账后填写 reviewedAt 和七项判断：故障原因已处理、完整备份已验证、账本与回执已核对、不确定 claim 已保留、确认与游标已核对、没有第二个写入端、继续使用已审查的当前数据。审核有效期 30 分钟；它是操作者声明，不是远程自动获得的事实。若需要换另一组候选数据，不能使用这条“保持当前数据”的解除流程。

clear 要求完整容器及 namespace 身份、恢复空间和输入检查通过。它只卸载命令、任务文件和实际 PID 均匹配的生产宿主，等待进程确实结束，再重新核验故障、维护、审核和完整数据。随后独占归档原故障与审核记录、删除该故障文件并重新加载相同宿主。原数据库不变，维护标记保留；新进程不会继承旧进程的内存故障状态。

完成后等待 production-host-status.json 出现本次启动后的 maintenance 且 storageFault=false，再使用已有维护 resume 入口；正常宿主负责依序启动业务。不要仅凭 clear 返回就声称微信或公网恢复。

若宿主停止后检查失败，故障与维护保持，服务继续停止。若故障归档后宿主重新加载失败，归档和维护仍保留，不能恢复数据库或删除维护掩盖错误；先核验归档、原只读发布、原任务文件和任务是否已加载，再由操作者重新加载同一个已验证任务。不得删除归档后强行重复 clear。该失败状态需要明确检查，工具不会接管未知任务或自动回退数据。

五项定向测试已覆盖未确认/过期/错批次审核、在线服务和低空间拒绝、停宿主后二次检查失败、重新加载失败的状态保留。归档文件及目录项在删除故障锁前完成同步落盘，已有归档或改变的故障文件均拒绝。实际三服务演练已通过解除后仍停在维护、单独 resume 后有序恢复；该演练使用合成审核与宿主替身回调。生产已经启用，但尚未遇到需要执行本故障解除入口的真实事件，不能把合成审核当作真实对账结论。
