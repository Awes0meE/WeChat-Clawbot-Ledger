# 语义化支出时间设计

日期：2026-09-04
状态：设计已确认，待实现

## 背景与根因

用户发送：

> 记账昨天晚上6点钟，晚餐10.5 备注麦当劳5卤肉饭5.5

账本中的金额、分类和备注正确，但时间被写成微信消息的发送时间 `2026-09-04 17:09`，而不是消费实际发生时间 `2026-09-03 18:00`。

问题不在模型是否理解了“昨天晚上6点钟”，而在写账接口没有表达这项理解的通道：

- `record_expense` 和 `prepare_expense` 只接收金额、一级分类、二级分类和备注；
- JSON Schema 禁止额外字段，所以模型不能传入消费时间；
- 插件当前无条件把可信微信消息时间写入 ezBookkeeping；
- 运行时提示词也没有要求模型对时间、币种作出显式判断。

因此这是工具合同缺失，而不是通过继续增加中文正则就能解决的问题。

## 目标

1. 让 Codex 在每条候选支出消息中先完成意图、时间、金额、币种、分类和备注的语义提取，再决定写账或追问。
2. 消息包含明确消费时间时，账本和回执都使用消费时间。
3. 消息未包含消费时间时，继续使用可信微信消息时间，不要求用户补充。
4. 相对时间以当前微信消息的可信发送时间和 `Asia/Singapore` 时区为基准。
5. 插件验证模型给出的时间证据、格式和合理性，避免模型凭空构造时间。
6. 保留现有可信消息关联、身份校验、单消息单笔写入、去重和权威回执机制。
7. 待确认支出的时间在重启、上下文压缩和下一轮确认后仍保持不变。

## 非目标

- 不在插件内实现完整的中文自然语言日期解析器。
- 不支持模型自行换汇，也不增加多币种账户或汇率服务。
- 不改变查询、收入、转账、退款或报销流程。
- 不改变 ezBookkeeping、微信通道或官方 Codex harness 的部署架构。
- 不放宽 owner、可信消息、金额证据、分类、去重或 API 成功校验。

## 方案选择

### 方案一：只修改提示词

不可行。即使模型正确理解时间，现有工具 Schema 也没有时间字段，插件仍会覆盖为消息发送时间。

### 方案二：插件解析所有中文时间

不采用。完整覆盖“昨晚六点”“前天下午”“9月1号中午”等表达会快速演变成脆弱的规则系统，并削弱模型的语义作用。

### 方案三：模型解析，插件验证并落账

采用。Codex 负责理解自然语言并给出结构化结果；插件只保留确定性的事实门禁。这个分层与现有金额、分类和备注流程一致。

```text
可信微信消息
  -> 插件把可信发送时间注入本轮上下文
  -> Codex 完成语义提取并选择工具
  -> 工具 Schema 接收显式的时间决策
  -> 插件核对原文证据、格式和边界
  -> ezBookkeeping 使用最终解析时间
  -> 权威回执显示同一个时间
```

## 可信参考时间注入

插件在 `before_agent_run` 中完成当前 owner 消息与可信入站记录的关联，并把记录绑定到本轮 `runId`。随后在 `before_prompt_build` 中，仅当本轮：

- 来自用户触发；
- 已与可信微信入站消息成功关联；
- 最终工具表面允许 `record_expense` 或 `prepare_expense`；

才通过 `prependContext` 注入一段短上下文。该钩子声明 `requiresToolAuthority: true`，并用主机提供的不可变工具权限确认本轮确实可调用上述工具：

```text
[可信记账时间上下文]
当前微信消息发送时间（Asia/Singapore）：2026-09-04 17:09
只用它解析当前消息中的相对消费时间；不得把它当作用户声明的消费时间证据。
```

注入内容不包含 sender ID、message ID、token、会话键或其他身份信息。若可信关联缺失，则不注入；现有工具门禁仍会阻止写账。

使用 `before_prompt_build` 而不是改写用户消息，可以保持用户原文不变，也不会让时间上下文进入普通微信消息文本或备注。

## 工具输入合同

`record_expense` 和 `prepare_expense` 使用相同的支出提案结构。金额、分类和备注维持现有字段，并新增币种及显式时间决策。

公共字段：

- `amount`：正数，两位小数以内；仍须与当前可信消息中的金额证据一致。
- `currency`：本阶段只允许常量 `SGD`。
- `primaryCategory`：正式一级分类。
- `subcategory`：该一级分类下的正式二级分类。
- `comment`：可选；遵守现有显式备注和事实提炼规则。
- `timeMode`：必填，只允许 `received` 或 `explicit`。

### `timeMode: received`

表示用户没有在当前消息中给出消费发生时间。插件使用可信微信消息时间。

不得因为模型懒得解析而选择此模式。插件会检测少量明显的时间提示词；若原文包含日期、相对日期或具体钟点线索，却选择 `received`，工具拒绝写入并要求模型重新理解或向用户澄清。

### `timeMode: explicit`

表示用户给出了消费发生日期或时间。还必须提供：

- `localDate`：模型解析后的本地日期，严格为 `YYYY-MM-DD`。
- `timeEvidence`：当前消息中与时间有关的原文片段；必须逐字存在于显式 `备注` 之前的正文中。

可选字段：

- `localTime`：只有用户给出了可确定的具体钟点时才提供，严格为 24 小时制 `HH:mm`。

这里由模型把“昨天”解析为日期，把“晚上6点钟”解析为 `18:00`；插件不需要理解这些词的全部语义，但会确认原文确实存在该证据。

## 时间解析边界

最终时间按以下顺序确定：

1. `received`：完整使用可信微信消息时间。
2. `explicit` 且同时有 `localDate` 和 `localTime`：使用指定日期与钟点。
3. `explicit` 只有 `localDate`：采用指定日期，但保留可信微信消息的时、分。

第三条是已确认的产品边界。例如微信消息在 `2026-09-04 17:09` 发出：

- `昨天晚饭10.5` -> `2026-09-03 17:09`
- `昨天晚上6点，晚饭10.5` -> `2026-09-03 18:00`
- `晚饭10.5` -> `2026-09-04 17:09`

插件使用 `Asia/Singapore` 构造 Unix 秒时间戳，写入 API 的时间与权威回执展示的时间必须来自同一个最终值。

## 硬门禁

模型负责语义，插件继续负责不可绕过的确定性校验：

1. 当前调用必须绑定到 owner 的可信微信消息。
2. `currency` 必须为 `SGD`。没有币种标记的本地金额由模型按 `SGD` 处理；用户明确声明其他币种时不得静默换算或写入，应先询问可入账的 SGD 金额。
3. `timeMode` 必须显式给出，不能依赖工具默认值。
4. `explicit` 的 `timeEvidence` 必须是当前原文中的非空连续片段，且不能从显式备注内容中借用。
5. 日期必须是真实日历日期；时间必须是合法的 `HH:mm`。
6. 当原文存在明显时间线索时，`received` 模式被拒绝。检测器只识别日期、相对日期和钟点线索，不负责将其转换成具体时间。
7. 最终消费时间不得比可信微信消息时间晚超过 5 分钟；这 5 分钟只容纳设备时钟误差，不把未来计划变成已发生支出。
8. 历史日期允许入账，不设置任意的“最多回溯天数”。
9. 金额证据、问句/确认流程、分类合法性、显式备注、消息去重和 API 成功回执继续沿用现有门禁。
10. 校验失败时不调用 ezBookkeeping，不产生“已记账”回执，也不自动重试写入。

## 模型处理顺序

运行时提示词明确要求 Codex 对每条消息按下面的顺序处理，但不展示思考过程：

1. 判断这是记账、确认/取消、查询还是普通对话。
2. 确认是否为本人已经发生的单笔支出，语气是否足够确定。
3. 提取并合计金额。
4. 判断币种；默认本地无标记金额为 SGD，明确的非 SGD 金额先追问。
5. 检查是否存在消费时间表达：
   - 没有：选择 `received`；
   - 有：以注入的可信发送时间为基准解析 `localDate`，只有具体钟点明确时才给 `localTime`，并附原文 `timeEvidence`；
   - 无法唯一理解：自然追问，不调用写入工具。
6. 选择正式一级、二级分类。
7. 提取显式备注，或仅根据原文提炼有依据的简短备注。
8. 明确支出调用一次 `record_expense`；语气不确定但其他字段完整时调用一次 `prepare_expense`。
9. 工具成功后逐字发送权威回执并立即结束本轮。

硬门禁用于防止不可信写入，不代替第 1 至 7 步的语义理解。

## 待确认与持久化

`prepare_expense` 在校验后持久化完整提案，包括：

- 整数分金额和 `SGD` 币种；
- 正式分类和备注；
- 已经解析并校验过的最终 Unix 时间戳；
- 时间模式及必要的审计来源标记；
- 原有会话键、源消息键、创建时间和过期时间。

用户随后回复“是”时，`resolve_expense_confirmation` 只能使用这条持久化提案，不能根据新一轮模型记忆重建时间。确认发生在第二天、网关重启后或上下文压缩后，也不会改变原提案的消费时间。

用户发送其他新内容时，仍按现有规则取消旧提案并处理新消息。

## 错误与澄清

- 时间表达无法唯一确定：模型自然追问，例如“你指的是哪一天/几点发生的呀？”
- 原文有时间线索但工具收到 `received`：工具拒绝，模型应重新解析；不得退回使用发送时间后伪装成功。
- 日期或钟点格式无效、证据不匹配、时间明显在未来：工具拒绝写入，向用户说明需要确认时间。
- 非 SGD：不换汇、不猜汇率，询问对应的 SGD 金额。
- 底层 API 失败：沿用现有安全错误文案，不泄露底层错误，不声称已记账。

## 回执

权威回执格式保持不变，但 `时间` 字段改为最终消费时间。例如样例消息应返回：

```text
记下来啦！🧾

- 账本：[ 日常账本 ]
- 支出：10.50 SGD
- 分类：食品酒水 - 早午晚餐
- 备注：麦当劳5卤肉饭5.5
- 时间：2026/09/03 18:00
```

回执仍由插件根据 API 成功结果生成和发送，模型不得自行拼装。

## 验收标准

自动化测试必须覆盖：

1. 样例消息在发送时间 `2026-09-04 17:09` 下写入 `2026-09-03 18:00`。
2. `昨天晚饭10.5` 写入昨天日期并保留消息发送时分。
3. `晚饭10.5` 完整使用消息发送时间。
4. 绝对日期与具体钟点可以正确写入。
5. `explicit` 缺少证据、证据不在正文、日期无效或时间无效时拒绝写入。
6. 原文存在明显时间线索而选择 `received` 时拒绝写入。
7. 明显未来的消费时间拒绝写入；合理的历史时间允许写入。
8. 明确非 SGD 金额不能写入，也不能自动换汇。
9. `prepare_expense` 保存最终消费时间；之后确认、重启或上下文压缩不会改变它。
10. API 请求的 `time` 与成功回执展示时间一致。
11. 原有直接记账、问句确认、金额算式、显式备注、分类、去重和权威回执测试继续通过。
12. 稳定微信消息 ID 插件的构建和入站 ID 测试继续通过。
