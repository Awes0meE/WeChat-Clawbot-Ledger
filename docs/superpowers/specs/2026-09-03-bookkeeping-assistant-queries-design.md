# 本地微信账本助理：安全写入与历史查询设计

日期：2026-09-03  
状态：待文档复核（总体方案已由用户确认）

## 1. 背景与问题

当前链路为：

`WeChat iLink -> Windows OpenClaw -> 专用本地 Qwen -> clawbot-bookkeeping -> ezBookkeeping`

现有代理只允许调用 `bookkeeping_health` 和 `record_expense`。因此，“午饭 7.2”可以进入写入工具，但“这个月我花了多少钱”没有对应的读取能力。现有运行提示又把无法记账或工具失败统一压缩成“记账失败，请重新发送一条新消息”，最终造成查询意图被错误呈现为写入失败。

运行日志还表明，ezBookkeeping 不可用时，本地模型曾重复调用写入工具。定制插件的消息 ID 去重避免了重复交易，但重复工具循环仍浪费时间，并生成误导性回复。

ezBookkeeping v1.6.1 已提供原生 Streamable HTTP MCP。其原生工具包括交易查询、账户、余额、分类、标签、汇率查询，以及新增交易。OpenClaw 2026.8.2 支持按 MCP 服务配置 `toolFilter.include`，并可在专用代理的工具策略中再次限制具体工具。

## 2. 目标

第一版把机器人从“只能写支出的工具”升级为本地账本助理：

1. 理解记账、历史查询、支出汇总和需要澄清的请求。
2. 保留现有写入路径的微信所有者校验、可信消息关联和消息 ID 去重。
3. 使用 ezBookkeeping 原生 MCP 提供灵活的只读交易查询。
4. 对常见统计问题使用程序确定性计算，避免由模型心算金额。
5. 生成简洁、活泼、可核对的中文微信回执，不展示思考、参数或底层错误。
6. ezBookkeeping 暂时不可用时明确说明“账本暂时连不上”，不把查询失败说成记账失败，也不反复写入。

## 3. 非目标

- 本轮不部署 Vercel，不开放公网端口，不实现家庭网页登录。
- 不增加修改、删除、批量导入或自动纠错交易的能力。
- 不允许云端模型读取账本；继续使用本地 Qwen。
- 不改动 ezBookkeeping 上游业务源码；优先使用官方 MCP 和稳定 HTTP API。
- 第一版不处理“一条微信消息同时要求记账并查询”的复合指令；遇到时先完成明确的记账请求，再提示用户单独发送查询。

## 4. 方案选择

采用“原生 MCP 只读查询 + 定制插件安全写入”的混合方案。

### 4.1 写入路径

所有新增支出继续调用 `record_expense`：

1. OpenClaw 验证当前发送者是所有者。
2. 插件通过 session 或 `channel + sender` 找到十分钟内的可信原始微信消息。
3. 插件以 `channel + messageId` 做持久化去重。
4. 模型只选择金额、一级分类、二级分类和可选语义备注。
5. 插件校验正式分类、金额、消息时间和备注长度，再调用 ezBookkeeping HTTP API。
6. 只有 API 明确确认创建成功后，插件才返回成功回执。

不将原生 MCP 的 `add_transaction` 暴露给 Qwen。它支持收入、支出和转账，但没有当前项目的微信消息关联和消息 ID 去重；工具超时后的重复调用可能产生重复交易。

### 4.2 灵活读取路径

启用 ezBookkeeping 原生 MCP。静态服务身份和工具过滤器由 `clawbot-bookkeeping` 插件声明，并通过 OpenClaw 的 requester-scoped MCP connection resolver 按可信发送者解析连接。只有同时满足以下条件的运行才获得 MCP URL 和临时使用的鉴权 header：

- 存在 OpenClaw 提供的可信 `requesterSenderId`；
- 消息通道是配置的微信通道；
- 发送者与本机 secret 中保存的所有者身份一致。

定时任务、子代理、心跳、公开 Gateway 调用和其他发送者没有共享后备连接，resolver 返回 `null`。在 MCP 服务级过滤器和 bookkeeper 代理工具策略两层只开放：

- `query_transactions`

明确排除：

- `add_transaction`
- `query_all_accounts`
- `query_all_accounts_balance`
- `query_all_transaction_categories`
- `query_all_transaction_tags`
- `query_latest_exchange_rates`

第一版仅需要交易历史；分类表已经由专用提示与插件提供。后续如果用户明确需要余额、标签或汇率，再单独评估并增开相应只读工具。

原生 MCP 服务继续绑定 `127.0.0.1:8180/mcp`，使用独立 MCP Bearer token。token 只保存在本机 secret 存储，由 resolver 在内存中读取；不进入仓库、提示词、持久化 OpenClaw 配置、日志或微信回复。

### 4.3 确定性统计路径

在 `clawbot-bookkeeping` 增加只读工具 `summarize_expenses`，用于“这个月花了多少钱”等常见统计。它复用现有固定环回 API 客户端，读取指定时间范围内的支出，然后由代码计算：

- 支出总额；
- 支出笔数；
- 按一级分类汇总；
- 金额最大的三笔支出。

这样，原生 MCP 负责灵活检索和逐笔问答，定制统计工具负责必须精确的金额聚合。两个读取路径都不具有修改或删除能力。

## 5. 意图路由

专用 Qwen 只处理个人账本域内请求，并按以下优先级判断：

1. **查询/统计意图优先识别。** 包含“多少、总共、花了、支出、记录、最近几笔、这个月、上个月、哪一笔”等询问语义时，不能因为消息中出现日期或数字就调用写入工具。
2. **明确消费才写入。** 消息同时表达已发生的消费和一个明确金额，例如“午饭 7.2”，调用一次 `record_expense`。
3. **常见汇总走确定性工具。** “这个月我花了多少钱”“本周吃饭花了多少”调用 `summarize_expenses`。
4. **灵活历史问答走原生 MCP。** “最近三笔是什么”“上周在 NTUC 买过什么”调用 `query_transactions`。
5. **信息不足则澄清。** 不猜测金额、日期范围或写入意图，不调用健康检查冒充查询。

所有回复只呈现最终结果。模型不得发送思考过程、工具名、JSON、参数校验、候选分类或重试过程。

## 6. `summarize_expenses` 接口

输入字段：

- `period`：`today`、`this_week`、`this_month`、`last_month`、`this_year` 或 `custom`；
- `startDate`、`endDate`：仅 `custom` 使用，格式 `YYYY-MM-DD`；
- `primaryCategory`：可选正式一级分类；
- `subcategory`：可选正式二级分类；
- `keyword`：可选备注关键词。

工具内部统一使用 `Asia/Singapore` 计算边界。自然周期使用左闭右开区间，避免月底、夏令时和毫秒边界产生重复或遗漏。查询限制为支出类型和配置中的固定 SGD 日常账户。

工具返回结构化明细和已经格式化的微信文本。模型最终回复必须原样采用工具文本，不重新计算金额。

## 7. 微信回复

### 7.1 记账成功

```text
记下来啦！🧾
账本：[ 日常账本 ]
支出：7.20 SGD
分类：食品酒水 - 早午晚餐
备注：无
时间：2026/09/03 16:21
```

备注规则：

- 用户显式写“备注”时，保存并显示其后的原文。
- 未显式写备注时，模型可从原消息中提取明确出现的商家或商品，不能补充消息中没有的信息。
- “NTUC 购物 8.25，买了两根芹菜，一个菜板”可生成“两根芹菜，一个菜板”。
- “午饭 7.2”没有更多明确信息，保存空备注，回执显示“无”。

### 7.2 默认月度汇总

用户已选择默认信息密度 A：总支出、笔数、分类汇总和最大三笔。

```text
这个月一共花了 123.45 SGD，共 12 笔 📊

分类汇总：
食品酒水：68.20 SGD
行车交通：31.25 SGD
学习进修：24.00 SGD

最大三笔：
09/02 数码装备：24.00 SGD
09/01 超市购物：18.60 SGD
09/03 早午晚餐：15.20 SGD
```

分类按金额降序显示所有非零一级分类。最大三笔按金额降序；相同金额按时间倒序。少于三笔时只显示已有记录。

### 7.3 空结果与失败

- 无记录：`这段时间还没有支出记录～`
- 账本不可用：`账本暂时连不上，本次没有写入或读取任何数据，请稍后再试。`
- 写入信息不足：针对缺少的字段自然追问，不再统一回复“请重新发送一条新消息”。
- 重复微信消息：明确说明已处理且未重复入账。

定制写入和统计工具把可预期的连接及 API 错误转换为稳定结果，而不是向模型抛出可诱发重复调用的异常。原生 MCP 查询错误由运行提示映射为相同的用户级失败文案；OpenClaw 的 MCP 失败暂停机制负责阻止连续协议重试。意外编程错误仍记录脱敏日志并失败关闭。

## 8. 服务可靠性

Windows 上的 ezBookkeeping 必须作为可恢复的后台任务运行：

- 登录后自动启动；
- 隐藏窗口；
- 异常退出后重启；
- 不受电池模式和默认执行时限终止；
- 启动后验证 `127.0.0.1:8180/healthz.json`；
- OpenClaw Gateway 启动与 MCP probe 只能在账本健康后判定成功。

模型不负责启动服务，也不能获得 shell 权限。服务恢复属于 Windows 部署层。

## 9. 安全边界

- ezBookkeeping 与 OpenClaw Gateway 均保持 loopback 绑定。
- 微信绑定仍只匹配用户自己的账户。插件通过 requester-scoped resolver 再次核对可信发送者，查询 MCP 连接只在所有者触发的当前运行中出现。
- MCP 服务级 `toolFilter.include` 和代理级 `tools.allow` 同时限制 `query_transactions`。
- 原生 MCP token 虽然在服务器端能够鉴权整个 MCP 服务，但不会暴露给模型；本机其他进程若窃取该 token 仍是残余风险，因此必须使用受限 secret 文件权限。
- API token、MCP token、微信账户 ID、发送者 ID、消息正文、SQLite 状态与账本数据库均不得提交。
- 成功回执必须以实际 API 写入或实际查询结果为依据。

## 10. 测试与验收

代码阶段按 TDD 完成，至少覆盖：

1. 本月、新加坡时区边界和自定义日期范围。
2. 金额从整数分转换为两位 SGD，避免浮点误差。
3. 总额、笔数、一级分类汇总和最大三笔排序。
4. 空结果、连接失败和 API 失败的稳定回复。
5. 查询请求绝不调用写入路径。
6. 同一微信消息最多产生一笔支出。
7. 原生 MCP 只发现 `query_transactions`，`add_transaction` 不可见。
8. 所有微信最终回复不含思考、工具参数或原始错误。

现场验收消息：

- `午饭7.2`
- `这个月我花了多少钱`
- `这个月吃饭花了多少`
- `最近三笔支出是什么`
- `上个月在NTUC买过什么`
- 重发同一条消费消息
- 暂停 ezBookkeeping 后分别执行查询和写入

验收还包括 `openclaw mcp doctor --probe`、Gateway 状态、微信通道 probe、两个插件的完整测试和干净工作区检查。
