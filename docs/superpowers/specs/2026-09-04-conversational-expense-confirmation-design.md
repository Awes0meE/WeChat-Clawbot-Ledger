# 对话式支出确认设计

日期：2026-09-04
状态：已实现的历史设计快照。对话确认与事务边界仍有效；其中的“本地 Qwen”运行时描述已被官方 Codex harness 取代。当前事实以 `README.md` 和 `WINDOWS-HANDOFF.md` 为准。

## 背景

现有系统同时使用本地 Qwen 模型和 `clawbot-bookkeeping` 插件处理微信记账。此前为防止查询、否定句、转述和不明确金额被误写入，插件开始使用大量确定性语句规则尝试理解中文。这种做法容易不断增加特例，也会压缩本地模型负责语义理解和自然对话的空间。

本设计将责任重新分层：

- 本地模型负责理解意图、判断是否模糊、选择分类、提取备注和发起追问。
- 插件负责身份、可信消息、金额一致性、分类合法性、待确认状态、去重和 API 结果等不可妥协的事务边界。
- ezBookkeeping 仍是唯一账本事实来源。

## 目标

1. 明确支出仍保持单轮快速记账，例如“午饭7.2”。
2. 模糊或询问式支出进入待确认状态，例如“午饭7.2吗”。
3. 用户可以用自然的“是”或“不是”完成确认或取消。
4. 待确认内容不依赖模型记忆，并在重启或上下文 compact 后仍可正确恢复。
5. 任何确认、重放或并发情形都不能产生重复支出。
6. 保留本地模型的语义价值，不在插件内重新实现完整中文理解器。

## 非目标

- 本轮不实现多条待确认队列。
- 本轮不增加收入、转账或报销流程。
- 本轮不把账本或待确认状态上传云端。
- 本轮不使用云模型替代本地 Qwen。
- 本轮不开发 Vercel 查账网页。

## 总体架构

```text
微信消息
  -> OpenClaw 可信入站元数据
  -> 本地 Qwen 判断意图和确定性
  -> record_expense | prepare_expense | resolve_expense_confirmation
  -> clawbot-bookkeeping 事务与去重层
  -> ezBookkeeping
```

### `record_expense`

仅用于模型判断为明确、已发生的单笔支出。插件继续核验 owner、当前可信消息、金额证据、正式分类、消息 ID 去重和 API 结果。插件可保留少量显而易见的硬拒绝，例如金额不匹配、同一消息有多个无法合并的金额，以及明确的问号式输入；但不再尝试证明整句中文的语义。

### `prepare_expense`

用于“金额、分类和备注已能解析，但用户是否要记账仍不明确”的情况。工具接收模型解析的候选表单，核验当前可信消息中存在相同金额、分类合法，然后持久化一条待确认项。它不调用写账 API。

### `resolve_expense_confirmation`

用于解决当前会话的唯一待确认项。参数只允许 `confirm` 或 `cancel`，不接受金额、分类、备注或时间。插件必须将模型的决定与当前可信微信文本交叉验证，并始终使用持久化提案的原始字段。

## 待确认数据模型

本机 SQLite 增加待确认表，至少包含：

- 会话键：根据可信 channel、account、sender 和 session 生成的哈希值。
- 源消息键：原始 channel 和 message ID 的哈希值，作为最终写入的去重根据。
- 原始消息时间：确认后作为支出时间。
- 金额：使用整数分值。
- 正式一级、二级分类。
- 经验证的备注。
- 创建时间与过期时间。

每个会话最多一条 active 提案。新提案以原子操作替换旧提案。提案默认 10 分钟过期。已确认或取消的提案从 active 状态移除；最终写入去重由现有 receipt 表负责。

待确认表、备注和身份键只存在于本机运行状态，不进入仓库。

## 状态机

```text
无待确认项
  | prepare_expense 成功
  v
待确认
  |-- 同会话肯定回复 --> 已确认 --> record transaction --> 无待确认项
  |-- 同会话否定回复 --> 已取消 ---------------------> 无待确认项
  |-- 其他新消息 -------> 被替换/取消 --> 处理新消息 --> 无或新待确认项
  |-- 10 分钟超时 --------> 已过期 -----------------------> 无待确认项
```

其他新消息包括新支出、查询、闲聊和任何非纯确认/取消文本。它们都会在新一轮开始时取消旧提案，不把旧内容带入新写入。

## 对话流程

### 明确支出

```text
用户：午饭7.2
模型：调用 record_expense
插件：确认 API 成功
助理：返回六行正式记账回执
```

### 模糊支出

```text
用户：午饭7.2吗
模型：解析后调用 prepare_expense
插件：保存待确认项，不写账
助理：返回完整确认表单
```

确认表单固定包含：

```text
帮你核对一下这笔～🤔
- 账本：[ 日常账本 ]
- 支出：7.20 SGD
- 分类：食品酒水 - 早午晚餐
- 备注：无
- 时间：2026/09/04 12:30
- 确认：没问题就回复“是”，不记的话回复“不是”就好～
```

### 确认

当前消息是纯肯定回复，且同会话存在未过期提案时，模型调用 `resolve_expense_confirmation(decision="confirm")`。插件从 SQLite 读取原提案，使用原消息时间和源消息键写账。成功后返回与直接记账相同的六行正式回执。

插件仅接受简短、独立的肯定文本，例如“是”、“对”、“确认”、“没错”。带有新金额、新消费或其他实质内容的消息不是纯确认。

### 取消

当前消息是“不是”、“取消”、“别记”或“算了”等简短否定回复时，模型调用 `resolve_expense_confirmation(decision="cancel")`。插件删除 active 提案并返回：

```text
好哒，已经帮你取消啦～ 这笔没有记到账本里 😊
```

### 新消息和更正

待确认期间发来任何其他实质内容，旧提案立即取消，新消息按普通流程独立处理。例如旧提案为“午饭7.2吗”，随后发“咖啡3.5”，系统不再保留午饭提案，直接处理咖啡。

“不是，是8.2”也属于新实质内容。它会取消旧提案；模型可以结合会话上下文生成新候选，但插件仍要求新金额 8.2 存在于当前可信消息中。

### 过期

提案建立超过 10 分钟后，任何确认都不写账。返回：

```text
刚才那笔确认已经过期啦，请重新告诉我这笔消费。
```

## 模型与插件的责任边界

### 本地模型负责

- 区分记账、查询、闲聊和更正意图。
- 判断是直接记账还是建立待确认项。
- 从自然语言中选择正式分类。
- 生成仅包含已知事实的备注。
- 缺少金额、对象或关键信息时发起自然追问。
- 不向用户展示思考过程、工具参数、候选分类或内部重试。

### 插件负责

- owner-only 权限与可信微信消息关联。
- 当前消息和提案金额的一致性。
- 正式分类及父子关系校验。
- 待确认项的原子创建、替换、过期、确认和取消。
- 按源消息 ID 去重，保证一条候选最多创建一笔支出。
- 只有 API 明确返回有效交易 ID 后才生成成功回执。
- 将网络、超时和未知结果分成已有的稳定终态。

## 替换规则

每个 owner 微信会话只保留一条 active 提案。每轮入站消息在 agent 开始之前按以下顺序处理：

1. 如果当前文本是纯肯定或纯否定回复，且有未过期 active 提案，保留提案供本轮解决。
2. 否则原子取消原 active 提案。
3. 新消息继续进入本地模型，不因取消旧提案而中断。

肯定和否定词表必须保持短小、封闭和可测试。包含金额、标点后新句子或新消费对象时，一律视为新实质内容。

## 并发、去重和恢复

- 建立提案使用 SQLite 原子 upsert，同一会话并发建立时仅最后一条可保持 active。
- 确认使用原子 claim；并发的两个“是”仅允许一个获得提案。
- 提案的源消息键继续通过 receipt 表实现最终写入幂等性。
- 如果确认在 POST 后断线，结果进入现有 unknown 终态，不允许再次 POST。
- OpenClaw 或插件重启后，未过期 active 提案仍可解决；过期提案在下次访问时清理。
- compact 只影响模型上下文，不影响 SQLite 提案。

## 回复与错误约定

- `prepare_expense` 成功后只返回固定确认表单，不展示思考过程。
- `confirm` 成功后只返回六行正式回执。
- `cancel` 返回固定取消文本。
- 无 active 提案时回复“现在没有等你确认的支出啦～ 放心，我什么都没记 😊”。
- 提案过期时返回“刚才那笔确认已经过期啦～ 我没有入账，需要的话重新发一次就好 😊”，不写账。
- 当前确认文本与 `decision` 不一致时 fail closed，不更改账本。
- 任何与账本 API 的失败继续使用已有的 not-written、unknown 和 written-confirmed 终态，不用模型自行推测结果。

## 提示词策略

`openclaw-workspace/AGENTS.md` 需要增加以下规则：

- 明确、已发生的支出调用 `record_expense`。
- 有问号、“吗”、“是不是”或其他真实不确定性，但足以形成完整候选时，调用 `prepare_expense`。
- 金额或支出对象本身缺失时，不调用工具，只做有针对性的追问。
- 当前是纯确认或取消回复时，调用 `resolve_expense_confirmation`。
- 收到新实质内容后不再引用旧提案。
- 工具结果是最终事实；模型只能原样转达工具的确认表单、取消、过期或正式回执。

## 工具权限

专用本地记账 agent 的允许工具面增加：

- `record_expense`
- `prepare_expense`
- `resolve_expense_confirmation`
- `summarize_expenses`
- `ezbookkeeping__query_transactions`

`bookkeeping_health` 仍为直接诊断工具，不给普通微信对话使用。不开放 ezBookkeeping 的广泛写入 MCP 工具。

## 测试设计

### 状态存储

- 同一会话只有一条 active 提案。
- 新提案原子替换旧提案。
- 重启后可读取未过期提案。
- 过期提案不能被 claim。
- 并发 claim 只有一个成功。

### 工具行为

- `prepare_expense` 不发送任何写账 HTTP 请求。
- 提案金额必须和当前可信消息一致。
- 无 owner 身份、无可信消息或分类不合法时不建立提案。
- 肯定文本、否定文本和 `decision` 必须一致。
- 确认使用提案字段，忽略模型上下文中的旧参数。
- 确认使用原消息时间，不使用“是”的时间。

### 交互回归

- `午饭7.2` 直接写入。
- `午饭7.2吗` 建立提案并显示全表单。
- 提案后回复“是”写入且只写一次。
- 提案后回复“不是”取消。
- 提案后发“咖啡3.5”取消旧提案并处理咖啡。
- 提案后发查询消息也会取消旧提案，且不写账。
- 10 分钟后的“是”不写账。
- 重复“是”、重放原问句和并发确认都不重复写入。
- OpenClaw 重启和 compact 不会使提案丢失或串到其他会话。

### 现有回归

- 保留现有 owner-only、trusted message、FIFO/run/tool-call 绑定、API timeout、交易 ID、receipt 和 SQLite 并发测试。
- 保留统计查询、MCP 连接、分类和 Windows 运行脚本测试。
- 删除或改写把插件当作完整中文语义判定器的测试，但不删除真正事务安全测试。

## 验收标准

1. 明确支出仍可以一条消息完成。
2. “午饭7.2吗”不写账，而是返回包含账本、金额、分类、备注和原消息时间的确认表单。
3. 同会话 10 分钟内回复“是”后只创建一笔支出，并返回六行正式回执。
4. 回复“不是”、新实质内容或超过 10 分钟都不写入旧提案。
5. 确认使用原消息时间和原提案字段，不依赖模型上下文。
6. 重启、compact、重放和并发确认不丢失提案、不串会话、不重复写入。
7. 模型负责语义判断；插件的确定性规则仅保留硬事实和事务安全边界。
