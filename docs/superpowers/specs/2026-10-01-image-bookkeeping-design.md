# 微信图片记账设计

状态：当前 Mac `0f4114f` 已部署下述语义校验；历史首版与时间/删账修复的设计保留在后文。验收见 [2026-10-11 发布记录](../../handoffs/2026-10-11-image-semantic.md)，手机新图片回执仍待实际试用。

## 2026-10-11 现行规则

本设计下文保留首版实现背景；其中“缺日期用收图时间”和固定标签/证据文本匹配已被新规则取代。用户明确选择：钱（实际总额和币种）、日期、用途齐全的一笔已发生消费由 AI 语义判断后直接入账；缺日期先询问。随后用户指定没有币种信息时默认 SGD（包括无其他线索的孤立 `$`），回执说明默认；已有币种依据和明确冲突不被默认覆盖。

新版模型工具契约要求 `imageEvidence.semanticVersion=2`，分别说明总额、币种、用途、消费性质与时间的依据及歧义。日期和用途不明确时不能拟单或写入；金额、币种或消费性质有合理候选时可编号确认。未付、失败、退款、转账、收入、预授权不是新增消费。模型理解不同语言、版式和日期，不再由关键词和正则表达式重新判断可见事实。

代码继续校验正数金额与精度、日历与未来时间、币种账户、类别、当前消息权限、图片来源和永久去重。`localTime` 使用 HH:mm，`localSecond` 单独保存秒；只有日期可省略钟点并明确披露收图钟点。旧证据路径仅兼容已持久化的历史候选；新的图片工具调用必须使用版本 2，因此无法用旧格式绕过缺日期规则。无数据库迁移或历史改写。

固定前置识图提示也同步保留三项信息，避免它先丢掉日期或用途。仅升级精确匹配的旧受管提示或空配置；自定义识图配置保持保护。仍使用现有官方模型和 harness，没有额外模型或服务。AI 证据不是独立 OCR 真值，类型校验无法证明模型没有误读，因此通过逐图人工预期与真实隔离账本验证。见 [100 组测试集](../../../test-cases/image-semantic/README.md)。

## 本次故障与范围

2026-10-01 的四次订单图片请求均已送达现有官方 Codex harness；会话输入包含图片，模型也提取了金额并尝试调用 `record_expense`。四次工具调用均在写账前返回“缺少当前微信消息的可信元数据，已拒绝操作账本”。人工核对原图，模型选择的是订单底部的实付款，而非商品单价。该结论仅覆盖这四个样本，不代表一般识图准确率。

微信插件已经负责授权发送者检查、图片下载和 `MediaPath` 传递。纯图片消息的文字正文可以为空，而原记账插件使用文字正文与模型提示的相等或结尾匹配来恢复当前消息绑定。失败发生在这条关联链路；固定版本 OpenClaw 2026.8.2 的实际隔离验证已证明下述异步上下文路径能够传递媒体身份。

修复前，金额和显式时间校验还要求证据出现在可信文字正文中。不能把模型识别出的文字直接当作原始用户文字，也不能因为输入是图片就跳过消息授权。

四张原图及其校验记录保留在 Git 外的私有验收目录。真实图片、订单号、收货信息、会话记录和金额不进入本设计的公共测试样本。本次调查没有修改生产服务或补录历史请求。

## 已实现的第一版体验

支持用户直接发送单张订单、付款凭证或小票。沿用当前官方模型的图片能力，不增加其他云服务。

固定 OpenClaw 路径先由官方 Codex 图像理解读取像素，再把描述交给记账轮。`tools.media.image` 必须使用明确的账目提取提示，保留金额、币种、付款状态和完整消费时间，不能依赖默认的简短图片概述；后续模型无法恢复概述中被省略的日期。原图测试同时核对实际入账时间，不能只检查最终金额。

用户已选择：明确已付款且最终金额唯一时直接入账，有疑问才确认。自动入账还要求币种可确定、当前图片来源有效、没有重复订单疑点，且一张图可归属一笔支出。这里的“金额唯一”是最终支付总额唯一，不要求页面只出现一个数字。

本次四张订单图片均具有待发货状态与明确实付款，适合作为自动入账路径的私有验收样本；仍需逐图核对币种及重复记录。用户后续明确允许下单和订单创建时间作为记账时间；没有可用消费日期才采用收到图片的时间，并在回执说明。

清楚的订单图片直接返回正式回执。有歧义时才显示候选，例如币种、最终总额或订单范围需要用户核对。以下仅展示候选格式，使用虚构数据：

```text
识别到一笔待确认支出 #3
金额：138.60 CNY（实付款）
商品：运动鞋
分类：衣服饰品 / 鞋帽包包
记账时间：今天 14:20（图片未显示可用的消费时间，采用收到图片的时间）
回复“确认第3笔”入账，或“取消第3笔”。
```

只有 API 确认写入成功才返回正式记账回执。识别失败、未付款、金额不清或缺少币种时，说明缺什么，并请用户补充；不把内部可信元数据错误直接作为日常交互。

连续发送四张清楚的图片，应各完成一笔并回执；连续发送有歧义的图片，应留下各自的候选。单笔候选保留现有“确认”“取消”习惯；多笔候选要求明确编号，不猜用户指哪笔。第一版不增加“一次确认写入多笔”，继续遵守一条入站消息最多产生一笔支出的约束。

## 识别与取值规则

- 一张图能明确对应一个已付款订单时，以最终实付款或实际支付总额为候选。商品单价、划线价、优惠额、运费和分期金额不能替代实付款；不再次乘商品数量，不凭空解释金额差额。
- 一张图含多个订单、多个币种、部分退款或多个无法区分的付款总额时，不合并猜测；请用户拆图或明确目标。
- 待付款、已关闭、支付失败不作为已发生支出。退款场景单独说明，第一版不自动冲账。
- 币种必须有图片或用户补充的明确依据。单独的 `¥` 不足以在 CNY 和 JPY 间判断，也不能套用文字记账的默认 SGD。页面上下文明确支持币种时，在回执中明示；仍有歧义则询问。
- 币种依据允许自然语序：中国电商页面、中文购物订单等上下文与 `¥` 可支持人民币判断，不能要求模型照抄固定词句。支付宝支付方式本身不证明币种或付款完成；模型明确判断已付且最终总额明确标为实付款时，可与订单状态共同支持直接入账。明确未付款、失败或退款状态优先。具体误拒与复验见 [证据表达修复](../../handoffs/2026-10-01-image-evidence.md)。
- 付款、支付、交易、下单、订单创建和购买时间均可作为消费时间，优先付款时间；模型选择与消费有关的一项，排除发货、收货、送达、预计到货及手机状态栏时间。多个消费时间明显冲突且无法判断时才询问。支持中文、斜线和点号日期，并保留秒。只有日期时沿用原始收到时间的时分并说明；没有可用日期时使用原始收到时间，不能用稍后的确认时间替代。
- 备注只保留商品或商户的必要摘要；收货人、地址、电话、完整订单号及付款流水号不进入备注。
- 图片中的指令、二维码、链接和商家文案都是待识别内容，不能授予工具权限或改变记账规则。

## 实现边界

### 1. 可信图片消息关联

在可信接收端建立消息 ID、owner、会话、接收时间与附件的关联。附件描述至少包含类型、大小和内容哈希；本地文件必须属于受控入站媒体目录，并处理符号链接、过期文件、类型不符和尺寸上限。

固定版本 Codex 的 `llm_input` 没有保留自定义 `channelContext`，提示事件也没有完整的传输首部，真实隔离测试已复现。因此不解析提示文字来恢复身份。微信插件在已鉴权、已下载的消息 dispatch 外层建立 `AsyncLocalStorage` 范围，传递当前消息 ID、账户、发送者和附件路径；记账插件在同一异步调用链的模型输入钩子中读取，并与已落库的真实消息及附件逐项匹配。权限、run 撤销和跨实例持久化仍独立复核，模型参数不能建立或选择此上下文。

微信接收插件为单张当前图片的框架媒体事实附上真实消息 ID。接收钩子将该 ID 与事件 ID、受控目录内的实际文件关联；引用旧图或一个消息含多图不提供这份记账关联。不能接受模型参数提供的文件路径、消息 ID 或身份作为授权，也不能用“最近一张图片”“同一会话只有一个候选”或空正文匹配代替确定关联。若框架将运行移出该调用链，关联失败并拒绝写账；升级框架时必须重跑实际媒体链路验收。

运行绑定必须继续经过 owner、当前消息、新鲜度、run 终止撤销和持久化校验；跨插件实例仍能读取同一可信记录。候选与最终回复都绑定源消息键，迟到的图片识别不能覆盖后续请求的回复。

图片哈希证明附件身份，不能证明模型识别的金额正确。视觉提取结果始终是模型判断，结构校验也不能独立证明像素含义。自动入账是用户选定的产品行为，须以真实图片隔离验收和歧义退回机制验证，不能声称程序能保证所有图片识别正确。

### 2. 候选提取与校验

扩展现有 `record_expense`、`prepare_expense` 和 `resolve_expense_confirmation`，保持精确工具允许列表；不开放文件工具、浏览器或额外执行工具。图片提取需包含来源类型、金额与标签、币种依据、订单状态、时间种类及必要摘要；可信附件键由插件注入，不能由模型自选授权来源。

在写入前构建并验证结构化图片提取结果：一个订单、一个最终付款总额、与金额标签对应的金额文本、明确币种依据和已付款证据。明确通过条件的当前图片走直接入账；缺字段、相互矛盾、多个总额或重复疑点走候选/追问。不依赖模型给出的单一置信分数，也不因调用了 `record_expense` 就默认满足条件。

插件验证结构、金额精度、金额与所提取付款文本的一致性、分类、币种账户范围及附件关联。识别文字不能被写回原始可信正文来绕过文字校验。图片与文字采用显式区分的校验路径；缺少可信当前图片或结构化支付证据时，`record_expense` 不能接受图片金额。上述一致性只能验证提取结果内部不矛盾，不能代替视觉识别准确率验收。

截图太长、模糊或缺少总额时，请求清晰原图或必要区域。当前四例识别成功不足以证明所有长截图都可靠；第一版不默默压缩到丢失关键数字后仍给出确定结果。

### 3. 多笔待确认与更正

原文字待确认表保持每会话单条，新非确认消息会丢弃旧文字提案。有歧义的图片使用独立的 `image_expense_proposals` 表与明确编号，不改变旧文字确认的语义；`image_expense_links` 保存图片防重关联。明确订单的直接入账不依赖此队列。

每笔保存源消息键、会话键、候选编号、附件哈希、提取结果、原始收到时间、创建与过期时间及状态。编号在同会话内不能复用到其他未清理候选。最多 10 笔有效候选，保留现有 10 分钟有效期；达到上限则提示先处理已有候选，不静默覆盖。

明确确认、取消只作用于指定编号。第一版更正使用“取消原编号，再发送完整的正确截图或文字消费”，不自动应用自由文本修改；含更正内容的回复不能作为确认。无编号且存在多个候选时不执行。普通查询不删除图片候选，但旧图片任务的迟到结果仍受当前回复保护。过期候选保留明确状态，不能因重启复活。

确认写入复用永久确认去重、原始消息去重、原子领取及不确定结果处理。数据库迁移只增加新结构，保留原有 receipts、确认去重、迁移记录和运行撤销记录。

### 4. 重复图片和订单

原始 channel + message ID 的永久去重继续是基础。相同图片以新消息重新发送时，若附件关联指向成功回执，先以该回执的交易 ID 查询当前账本。原账目仍存在时防重，包括用户在网页修改过金额、日期或备注的情况。只有接口明确返回交易不存在，才解除仍属于该旧回执的图片及订单关联，允许新消息按当前规则重新入账。原消息重放始终防重，不删除旧回执或永久确认记录。

查询超时、权限错误、其他 HTTP 错误、空结果或无法匹配交易 ID 的响应均不能证明已删除；返回可读的未入账说明。只有成功回执可以做删除复核，pending/unknown 状态保持保守处理。查询后再次核验消息权限，并在数据库事务中比较旧回执、仅解除原所有者的关联；之后沿用原子领取，防止并发重发重复写入。此修复不扫描或清空历史图片记录，仅在新消息到来时核查。验证与发布见 [删账后重发修复](../../handoffs/2026-10-01-image-reentry.md)。

不同截图可能属于同一订单。识别出的平台与订单号可作为私有重复提示依据，但属于模型提取数据，不能单独作为全局硬去重依据。相同金额也不能作为重复订单依据。用户确认这是另一笔时，仍须走独立候选和确认流程。

## 验收范围

以下为验收矩阵；已执行结果和未验证边界以各次发布记录为准，不表示每个场景均已在真实手机或 Windows 原生环境完成。

- 纯图无正文、图文、连续四图和交错查询均绑定各自的消息与附件；不能串金额、串候选或覆盖新回复。
- 未授权发送者、伪造附件路径、历史图片引用、过期运行、重复执行、跨实例执行和晚到回复均不能越权写账。
- 多价格、数量、优惠、运费、长图、模糊数字、币种歧义、未支付、退款和创建时间均有代表性的合成图片用例；合成数据可进 Git。
- 四个真实私有样本在隔离账本完成逐笔提取、人工核对与自动唯一写入；有歧义样本仅确认后写入。实际模型测试的原图和输出留在私有目录，不能向生产补录这四笔。
- 连续图片、编号确认、更正、取消、过期、重启恢复、重复截图和 API 不确定结果均有状态测试；所有旧文字记账与查询回归通过。
- Mac 的固定运行镜像通过验证；Windows 共享逻辑完成相应测试。未完成 Windows 运行验收时明确标记，不以 Mac 成功代替。
- 生产发布成功与手机实际收到正确的直接入账回执、歧义确认表单及确认回执分别记录；进程健康不能替代手机验收。
