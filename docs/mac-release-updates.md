# Mac 生产版本更新与回退

此流程更新 Clawbot 源码与对应 runtime/guard 镜像，保留当前固定 OpenClaw、官方 harness、模型、数据库引擎和业务配置。更换这些上游版本、数据库结构转换或增加工具不属于本次搬迁的隐含授权。2026-09-09 已在实际生产数据上完成 `9f3c0e5` → `62cfd9e` → `4870258` → `8a9b796` 三次正向更新：每次均使用当时最新备份，新卷完整比对、维护切换、恢复服务与公网检查通过，旧卷和镜像保留。详见 [切换记录](handoffs/2026-09-09-production-cutover.md)；下方演练矩阵保留为先前的失败回退证据。

## 离线准备

先进入当前生产宿主的维护模式，生成并验证当前九卷备份，再用旧镜像从这份备份独立恢复出保留候选。已有的原卷、镜像和源归档都保留。

从已检查、回归通过的目标源码提交构建两幅固定镜像并导出恢复资料。在该提交的干净检出中，使用现有 `prepare-production-host.mjs`，传入原切换 ID、原快照/导入清单哈希、新恢复 UUID 和当前备份清单 SHA-256，生成新的未安装宿主。目标源码可比当前新，也可以是经兼容性核验的旧版本；选择旧代码仍以当前数据生成新卷。

```text
node scripts/mac/prepare-release-update.mjs prepare <当前宿主> <新版本宿主> <当前备份的保留候选回执>
node scripts/mac/prepare-release-update.mjs stage <当前宿主> <新版本宿主> <同一候选回执> <私有审核JSON>
```

prepare 只写全部未确认的审核模板。检查点要求核验精确版本差异和测试、固定上游及数据兼容性、使用当前备份、保留原卷和镜像、仅离线准备。stage 要求 30 分钟内确认，绑定两个源码/镜像版本、原切换/导入、新批次和备份；不能用历史回退的审核授权版本更新。

stage 只创建不存在的九个目标卷，从只读候选复制并核对完整数据；随后仅在新卷中调整 guard policy 和 activation 的 sourceCommit，其余字段原样保留。两库、未知表、权限、附件、授权、微信游标、去重/确认和导入凭证均不得变化。最后签发新源码/批次的九份只读完成凭证，再比较每一个源/目标文件和元数据，源候选的完整审计仍须不变。CLI 还要求新镜像的正式输入预检通过，成功才保存 stage 回执。

更新包只做这两项源码绑定调整，不是通用配置编辑器。既有配置不适用于新版本时，输入预检拒绝；不得手工放宽策略以通过。失败保留本次未启用目标，不能重复 stage 覆盖。审核中的兼容性判断仍须有对应版本和数据的测试证据，不能由文件哈希相同代替。

## 在维护中切换版本

stage 成功后，继续使用同一当前备份和新 stage 回执：

```text
node scripts/mac/switch-release-host.mjs prepare <当前宿主> <新版本宿主> <当前九卷备份目录> <新stage回执>
node scripts/mac/switch-release-host.mjs switch <当前宿主> <新版本宿主> <当前九卷备份目录> <新stage回执> <私有切换审核JSON>
```

切换审核与离线准备审核分开，默认全未确认。切换前重新认证当前备份、核对当前九卷与备份完全一致、新 stage 源审计及所选归档必须就是当前备份，两库不允许改变。它不会将一份较早的历史数据当成普通更新；同版本历史恢复仍使用独立的 `switch-recovery-host.mjs`。

随后核验精确宿主任务和三服务身份，卸载旧宿主并等待退出，只移除已识别且停止的旧容器与空网络，旧卷和旧镜像保留。新镜像只创建停止容器；两边数据复核后，替换维护/启用记录中的源码与批次、安装并加载新宿主。工具要求新进程 PID 对应的新鲜 maintenance 状态，才报告切换已验证。它不启动业务。

新容器只创建一部分、新任务加载失败时，若两边数据、维护/启用和任务文件仍符合原核验，恢复旧容器、旧源码/批次选择和旧宿主，仍保持维护。出现数据变化、未知资源、复核失败或进程中断则保留现场。阶段、原任务及记录副本保存在私有 journal，不自动重放半完成操作。新宿主加载后的状态无法确认时，也不自动解除维护。

最后明确恢复业务使用：

```text
node scripts/mac/production-maintenance.mjs resume <切换结果中实际选中的宿主>
```

普通宿主按 readiness 顺序启动账本、接收器和守护。版本回退仍需验证对应版本的配置与数据兼容性；仅文件相同或启动健康不能替代记账与权限回归。

## 新版发生写入后的回退

新版开始处理消息或账本写入后，升级前的旧卷已不代表当前状态。先维护停写、核对在途回执并备份当前九卷，然后用当前备份生成保留候选，为经兼容性验证的旧代码版本准备另一个新 UUID，再按上面的 stage/switch 流程操作。目标仍保留最新交易、确认、去重和游标状态，不直接重新选择冻结的升级前旧卷。

涉及数据库结构转换、不兼容配置或目标缺少本流程离线检查工具时会拒绝。需要先完成该具体版本的迁移与兼容性方案，不改旧凭证绕过检查。首次生产候选应包含完整更新工具；先前尚未启用的准备镜像不自动成为支持回退的生产版本。

## 准备期验证范围（2026-09-08）

七项定向测试覆盖严格版本审核、源/目标绑定、当前备份限制、数据变化拒绝与新宿主失败后的维护回退。共用三服务驱动在实际 ARM64 Docker 中已通过不同镜像/合成源码标识的成功选择、部分容器创建失败回退和新宿主加载失败回退。宿主回调为替身，macOS LaunchAgent 生命周期使用已有单独的真实 A→B→A 验证；正式生产 CLI 尚未端到端执行。

九卷演练已通过完整正反方向：含 crash-left WAL 的旧批次 → 新镜像/新源码绑定 → 提交一条升级后的合成记录 → 当前九卷备份/独立恢复 → 旧版本标识的新批次。最后数据库审计与升级后状态完全一致，原候选和非绑定文件保持不变。两次实际失败揭示了 tar 提前关闭流及干净 WAL 在只读目录创建辅助文件的问题；二者已修复并有分别的拒绝/恢复回归，完整九卷往返随后通过。

运行入口为 `verify-migration-import.mjs --verify-release-update`。实验镜像 `clawbot-release-update-rehearsal:p5` 从 generation 演练镜像附加当前 Docker 工具；`clawbot-release-update-previous-rehearsal:p5` 以不同专属标签产生第二个镜像身份。三服务的 `clawbot-guard-update-rehearsal:p5` 同样使用专属标签区分镜像。它们验证版本选择和数据流，不代表已经验证任意两个真实发布之间的业务兼容性，不能用于生产。

三服务切换演练使用 `verify-managed-runtime.mjs --verify-release-update`；`--switch-only` 只跳过此前已通过的故障矩阵，仍从全新合成服务开始验证两种失败回退、成功选择和单独恢复业务。所有演练都不调用真实微信发送或公网 Tunnel。

本次最终验证：显式 resume 后新镜像三服务健康，再进入维护成功，旧卷完整哈希不变。最新可移植回归共 549 项，548 通过、0 失败、1 跳过，另排除 11 个 Windows 操作文件。九卷正反方向、两种失败回退、升级后记录保留均已实际通过；合成资源已清理。
