# 保留旧卷的恢复批次

首次生产导入继续使用原有九个 `clawbot-production_<role>` 卷。恢复历史归档时，不覆盖或删除这些旧卷，而是显式指定恢复 UUID 和已选归档清单 SHA-256，准备独立的 `clawbot-production-recovery-<UUID>_<role>` 九卷。服务项目、固定端口、容器内路径和唯一生产接收器合同保持原定义。

每个新卷必须具有匹配的项目、角色、切换 ID 和恢复批次标签。宿主 Compose、容器挂载检查、输入预检、备份和存储故障审核全部使用所选批次。启用记录额外绑定恢复批次与源归档清单；旧启用记录不能授权新的恢复批次，混用旧卷也不能通过检查。

新批次还要求九份只读 `recovery-generation.json` 完成凭证，全部内容一致并绑定源码、导入/切换、恢复 UUID 和所选归档。任一凭证缺失、可写、为链接或来自其他归档，生产预检都会拒绝。这些凭证必须由后续候选复制工具在完整文件和两库验证成功后写入，不能为了启动手工补齐。

只读宿主准备入口可附加恢复 UUID 与源归档清单 SHA-256：

```text
node scripts/mac/prepare-production-host.mjs <镜像发布目录> <原切换ID> <原快照SHA256> <原导入清单SHA256> <恢复UUID> <所选备份清单SHA256>
```

它仅生成独立、未安装的宿主包，不复制数据、不替换任务、不改变启用或维护记录。恢复批次使用同一份已验证代码/镜像；跨版本升级是另外的操作。

批次描述、身份/门禁/完成凭证验证、备份接口、候选复制和凭证签发已实现。人工审核后的同版本宿主切换与失败回退也已实现，见下方操作顺序。当前生产镜像已包含凭证预检。本页同版本历史恢复保留合成验收范围；已经执行的真实跨版本更新见 [版本更新](mac-release-updates.md)，不要混称两者。

## 从保留候选准备新批次

先用历史归档恢复入口的 `--retain` 保留验证通过的候选。仓库外的 recovery-checks 回执现在包含原归档清单 SHA-256、完整数据审计、原批次和镜像身份。使用同一归档版本的代码/镜像准备上面的未安装宿主；不要把恢复和升级合并成隐式选择。

```text
node scripts/mac/prepare-recovery-generation.mjs prepare <未安装的新批次宿主> <私有候选回执>
node scripts/mac/prepare-recovery-generation.mjs stage <同一宿主> <同一候选回执> <私有审核JSON>
```

prepare 仅生成全部未确认的审核文件。操作者确认选择的归档、当前数据保留、不确定 claim 的处理和仅离线准备后，填写 reviewedAt 并运行 stage。审核有效期 30 分钟，绑定候选、数据审计、归档、源码和目标批次；此确认不等于授权开始收发消息。

stage 核验源候选仍为 recovery 标签、九卷未被运行容器使用、实际镜像匹配，并要求全部目标卷不存在。创建后再次检查精确标签与空目录，源只读、目标可写，完整流式复制。源/目标全文件、权限和两库审计一致且源保持不变后，先同步目标持久内容，再在九卷写入只读完成凭证并复核。候选来自更早的恢复批次时，只替换新目标中经过核验的旧批次凭证；源候选和旧生产卷原样保留。

成功回执保存在仓库外 generation-stages；失败会保留本次新目标供检查，不覆盖、不删除旧卷，也不启用目标。缺失凭证的半成品不能通过生产预检。若目标已存在，不通过重复 stage 继续覆盖，应先检查失败现场。

实际 ARM64 合成演练已通过：未确认拒绝、从含已提交 WAL 的保留候选复制、源/两库不变、九份凭证、重复创建拒绝；随后对新批次做九卷加密备份、独立恢复和第二批次复制，核验旧凭证只在新目标更新。全部演练资源均带随机合成标签并清理，没有生成真实生产批次。正式 CLI 尚未对生产数据执行。

演练使用 `clawbot-generation-rehearsal:p5`（从本机 P3 演练镜像附加当前 deploy/docker 工具构建），运行 `node scripts/mac/verify-migration-import.mjs --verify-generation`。这个实验镜像不可用于生产发布。

## 在维护中选择新批次

先进入当前宿主的维护模式，生成并验证当前九卷备份，再完成上面的历史候选恢复与 stage。若存在存储故障锁，先按 [故障核对流程](mac-storage-reconciliation.md) 处理。切换入口要求当前数据仍可完整读取，且与刚验证的当前备份一致；它不能越过损坏数据核对，自动用旧归档替换不可读的当前卷。

```text
node scripts/mac/switch-recovery-host.mjs prepare <当前只读宿主> <新批次只读宿主> <当前九卷备份目录> <新批次stage回执>
node scripts/mac/switch-recovery-host.mjs switch <当前只读宿主> <新批次只读宿主> <当前九卷备份目录> <新批次stage回执> <私有审核JSON>
```

prepare 生成全部未确认的审核；需确认选定数据、当前备份、旧卷保留、未定回执与游标处理、无竞争写入端及继续维护。审核有效期 30 分钟，绑定新旧批次、同一套代码/镜像、当前备份和目标完整审计。

switch 重新核验两边完整数据、所有卷无运行消费者、当前精确 LaunchAgent 和维护/启用记录。随后卸载旧宿主并等待退出，只删除已识别且停止的容器及空网络，所有旧卷保留；创建指向新卷的停止容器，复核两边数据，再按维护记录、启用记录、任务文件的顺序替换并加载新宿主。最后要求新进程 PID 对应的新鲜状态明确为 maintenance。切换成功不会开始微信收发或公开 Tunnel。

新容器创建或新任务加载失败时，仅在数据、记录和资源身份仍符合预期的情况下清理新建的停止容器并重建旧容器、恢复旧任务，仍保持维护。遇到未知容器、数据变化或状态核验失败则保留现场，不自动解除维护。操作阶段和原任务/记录副本保存在仓库外私有 journal；进程被中断后不自动续跑或复用旧审核。先根据 journal 检查现场，不能直接再次切换。

确认已选批次及维护状态后，恢复业务使用独立入口：

```text
node scripts/mac/production-maintenance.mjs resume <实际已选中的只读宿主>
```

恢复历史数据可能丢失归档之后的交易和去重记录。恢复前的人工对账与消息游标判断不可由全文件哈希代替；切换失败后也不能直接重启 Windows 旧数据。

验证范围：共用 Docker 驱动已在随机合成三服务项目上通过成功选择、只创建部分新容器后失败回退、新宿主加载失败回退和旧卷保留；另用专属随机标签的真实 macOS LaunchAgent 完成 A→B→A 加载/切换/回退。Docker 演练的宿主回调为替身，LaunchAgent 生命周期单独实测；没有把两项合成为“生产 CLI 已端到端通过”。实际生产 CLI 仍等待真实维护、备份、stage 与审核输入。所有合成资源已清理。

本次补充实测使用内容不同的新旧合成 SQLite 快照：成功选择、部分创建失败回退和加载失败回退后，分别与各自原哈希一致。可移植回归共 540 项，539 通过、0 失败、1 跳过，另明确排除 11 个 Windows 操作测试文件。
