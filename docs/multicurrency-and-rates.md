## 用户行为

- 文字消息没写币种仍默认 SGD。`午饭35rmb`、`午饭35人民币` 存 35 CNY；明确 ISO 代码支持 ezBookkeeping 1.6.1 全部 159 个币种，另支持明确的中英文名称及常用简称。名称对应多个代码时须用代码消歧；裸 `$` 按本地 SGD，共享 `¥` 不猜币种。
- 原币写入对应子账户，不先折成 SGD。ezBookkeeping 1.6.1 的金额接口统一按 1/100 保存、最多两位小数，包括 JPY、KWD；不按 ISO 小数位擅自截断或改写用户金额。币种目录及上游文件哈希在 `openclaw-plugins/clawbot-bookkeeping/currency-catalog.json`。
- 新建父账户“多币种支出”，包含 159 个零余额子账户。原“日常支出”SGD 账户及其历史保持原样，新 SGD 写入新 SGD 子账户。汇总覆盖旧账户和新子账户，只查询固定范围，不让模型任意选择账户。
- 文字金额不确定时，由既有 OpenClaw AI 选当前原文中最像实付的金额，先发完整确认单。“是”才写一次；“不是”、转聊或十分钟超时不写。F1 和件数不会使 288 的衣物支出被误拒绝。
- “我今天花了多少钱？换成人民币是多少钱”一次调用汇总的 `convertTo: ["CNY"]`，同一回复给出原币支出和人民币折合金额。`questions` 可合并最多 8 个 summary、find、history、exchange 问题；失败项单独说明，保留其他结果。
- 混合币种先分币种列出原始总额；无指定目标时折合 SGD。转换采用十进制有理数计算，按各币种小计换算到目标的两位小数再相加。若任一币种缺报价，不将部分换算冒充完整总额。单笔金额查找按原币准确匹配，不换汇匹配。

图片无币种信息时默认 SGD，并在回执披露；无其他线索的孤立 `$` 也按此规则。明确币种或页面依据按原币，冲突不能被默认覆盖；单独的 `¥` 不足以区分 CNY 和 JPY。有歧义的图片使用独立编号候选，普通查询不会清除它们，详见 [图片规则](superpowers/specs/2026-10-01-image-bookkeeping-design.md)。

## 中行来源与每日更新

微信换算默认 `exchangeRateSource: bank_of_china_spot_sell`。只从 [中国银行外汇牌价](https://www.boc.cn/sourcedb/whpj/) 的“现汇卖出价”列取数。官网报价单位为每 100 外币兑人民币；例如每 100 SGD 报价 531.29，计算使用 1 SGD = 5.3129 CNY。这是购买外汇成本的估算口径；反向查询也沿用同一卖出价口径，不切换为银行买入价。

OpenClaw 插件服务 `clawbot-daily-bank-of-china-rates` 每天 **00:00 Asia/Singapore**（与北京时间相同）取一次当时官网最新公布的报价。它是后台取价，不调用 AI、不发送微信通知。当天查询复用缓存；启动发现错过当天取价时补取一次。SQLite 的每日领取记录保证 Gateway 与分离的工具进程合计每天最多一次请求。

独立缓存文件为 `stateDbPath + ".rates.sqlite"`，放在现有回执持久化目录／Docker receipts 卷中；重启保留，九卷备份应一并保留。没有改动原回执库的确认、去重、可信消息或权威回复表。失败不覆盖上次成功报价，当天不反复重试，次日重新尝试；响应注明“今日更新未成功，使用上次成功报价”。首次取价失败且没有缓存时明确无法换算。银行发布时间始终显示，超过七天的报价另外注明过旧；本次抓取时间不冒充银行发布时间。

现汇卖出价为空的币种不能换算，绝不拿现钞卖出价、买入价、中行折算价或其他来源补齐。全部 159 种原币入账不依赖汇率完整性。公开取价只传普通 HTTP 请求头，不携带账本令牌、身份、交易金额、备注或用户问题。

可显式配置 `exchangeRateSource: ezbookkeeping` 使用现有 `exchange_rates/latest.json`。这是人工选择来源，无自动回退。**ezBookkeeping 网页的内置汇率配置没有修改**；中行适配服务于微信工具的汇总及换算。

## 账户准备和发布

维护脚本不属于微信工具，模型没有创建或改动账户的权限。先只读生成回执：

```sh
node scripts/prepare-multicurrency-accounts.mjs --origin http://127.0.0.1:18888 --token-path /operator/private/test-token
```

回执列明父账户、全部币种、159 个初始零余额子账户、旧账户保留、交易移动数为 0，以及 `planSha256`。显式传入 `--apply-sha256 <reviewed-hash>` 才提交一次创建请求，并再次读取核验；已有完整结构则不重复创建，部分或冲突结构拒绝修改。请求结果不明时先查账户，不盲目重试。令牌从私有文件内部读取，不打印。

生产必须先取得维护与发布授权，并按 [Mac 不可变更新流程](mac-release-updates.md) 通知、维护停写、备份当前九卷、生成新一代卷及镜像，完整比对后先切换至仍处于维护状态的新宿主。此时仅启动已验证的账本服务，以管理脚本准备账户；逐表确认原有记录保留，停止账本并备份新状态，再显式恢复服务。不得在 stage／switch 的完整数据比对前创建账户；保留所有旧卷和恢复材料。不得把测试脚本的地址改成生产，不直接覆盖活动源码或移动旧交易。Windows 发布白名单包含所有新模块，既有原生安装路径保留。

## 验证入口与范围

```sh
node scripts/run-portable-tests.mjs
node scripts/verify-multicurrency-isolated.mjs --run
```

第二项只创建自有临时 Docker 容器和 tmpfs，在 `127.0.0.1:18888` 运行固定 ezBookkeeping 1.6.1 镜像，使用合成注册信息。它真实创建 159 个币种子账户、逐币种写入原币支出、验证旧账户保留、10 条历史分页及三项合并查询；结束按容器 ID 与所有权标签清理。不会挂载生产卷或访问 `8888`。它验证的是账本 API 集成，不是完整 OpenClaw 镜像或真实微信验收。

单元回归还覆盖跨实例原币确认、拒绝错误币种、明确缺价、批量回复持久化、每日零点调度、跨进程每日去重、重启补取与失败保留。本次上线已观察后台首次取价成功；用户于 2026-09-13 确认修复后可用；各币种／复合问题的手机端逐项验收与实际零点触发仍须单独留证，不能由轮询正常或定时测试推断。Windows 原生测试与实际上线状态分别报告。
