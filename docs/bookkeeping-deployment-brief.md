# 记账部署方案：按最新用户要求

更新时间：2026-09-03。此文取代此前调研中“规则优先、Actual Budget 优先”的建议。Windows 已成为在线接收端并完成真实微信写入；Mac 接收端已停止。

## 已确定的用户偏好

- 每条消费消息都由模型理解金额、商品/商户、一级和二级分类。规则不充当优先分类器。下一阶段由模型从原消息提炼简短备注，但不得补充原文没有的事实。
- 默认 SGD；时间使用 Asia/Singapore。
- 输入形如“午饭12.8”“NTU衣服35”“NTUC购物8.25，备注买了两根芹菜，一个菜板”。
- 每笔保留时间和备注位置。超市购物整笔入账，不按备注拆账，也不因混合商品追问分类；统一可归“食品酒水 / 超市购物”。
- 优先部署现成应用及作者提供的集成，必要时 fork 后少量修改。
- Mac 经常合盖携带；考虑 Windows 承担常驻 Gateway、模型和账本。
- Mac 上已有 Bionic/Qwen 不改动。Windows 已实测为 Ryzen 9 6900HX、RTX 3070 Ti Laptop 8GB、32GB RAM。

## 首选：ezBookkeeping

项目：https://github.com/mayswind/ezbookkeeping

核实正式发行 v1.6.1（2026-07-20），提供 macOS ARM64 与 Windows x64 安装包。核验时 main 的最新推送日期为 2026-09-02；本次关键特性核验使用 v1.6.1 源码，避免把开发分支功能当作已发行功能。

正式发行已经包含：

- 原生两级分类，且可批量创建。
- SQLite 存储，多币种与时区。
- 交易发生时间、创建时间分别保存；交易备注字段支持 255 字符。
- 内置 MCP：add_transaction 支持 RFC3339 时间、二级分类、账户、金额和 comment；query_transactions 支持按时间/分类查询。
- 原作者提供 OpenClaw 兼容 Skill 与 Windows PowerShell、macOS Shell API 工具脚本。
- MIT License，保留版权和许可声明即可按许可修改。

官方 OpenClaw 接入：https://ezbookkeeping.mayswind.net/agent/openclaw
官方 MCP：https://ezbookkeeping.mayswind.net/mcp/

Windows 已安装原版 v1.6.1 并通过专用最小权限插件接入 HTTP API。OpenClaw 仍使用 `minimal` 工具配置；作者 Skill 已停用，没有开放通用命令执行，也没有重复启用 MCP 写入路径。真实微信消息已成功触发一笔写入并返回手机确认。

对比：此前 Flask 微信记账项目要补原生两级分类、币种、可靠时间、接入、模型优先处理及管理界面；FinancialClaw 也需要适配两级分类、消费时分秒与 Node 版本。基于目前已核验功能，ezBookkeeping 更省改动。

## 建议运行位置

手机微信 ↔ 腾讯 iLink ↔ Windows OpenClaw ↔ Windows 本地模型

Windows OpenClaw ↔ ezBookkeeping ↔ Windows 本地 SQLite

Mac 后续作为管理端和按需执行节点，离线不阻断 Windows 上的记账。屏幕可以关闭，电脑须不睡眠并保持网络；服务还须验证重启后能恢复运行。

Windows 模型、账本、工具和微信插件均已验证并处于当前使用状态；Mac 接收端已停止。同一微信机器人不得让两台 Gateway 同时轮询。

## 模型与数据边界

- 当前模型：Ollama `qwen3:8b` Q4、8192 context、thinking off、全 GPU。模型已成功调用只读健康工具和真实微信写入工具；更多消费类型的分类准确率仍需逐步验收。
- 每笔都送模型；不使用正则优先分类。
- 可以先对比非思考和短思考模式，非思考仍然是模型理解。不能把 Codex 的 medium 参数机械映射到 Qwen。
- 本阶段上下文只需当前消费、分类表和少量偏好，不继承全部项目历史。
- 程序验证金额、类别存在性、时间格式和消息重复；这些是数据校验，不代替模型分类。
- 时间优先采用微信 create_time_ms，缺失时取服务收到消息的时间并记录来源。当前腾讯插件确实将 create_time_ms 传入 OpenClaw 的 Timestamp；下一阶段需验证它正确进入记账请求。
- 不把“记录时间”宣称为实测消费发生时间。默认以消息时间记账；用户明确给出消费时间时才另行解析。
- 元数据中的时间和消息 ID 不由模型自由编造；若原生工具流程不能可靠绑定它们，才加一个很薄的适配层。
- 备注复用现有 comment 字段。当前实现仅提取显式“备注”后的原文；下一阶段让本地模型从整条消息提炼短备注，例如“午饭食阁6.5+2.5”得到“食阁吃饭”，“NTUC购物8.25，买了两根芹菜，一个菜板”得到“两根芹菜，一个菜板”。没有有效细节时 comment 留空、微信回执显示“无”。
- 超市购物即使同时包含食材、日用品，也只保存一笔总额，归“食品酒水 / 超市购物”；备注不触发拆账或分类追问。用户不需要商品明细管理。
- 已核验现有 comment 上限为 255 字符，足够当前短备注；实现时不得静默截断，超长备注的处理仍需单独验证。
- 专用适配层以稳定的 `channel + message_id` 做 SQLite 持久去重，并设置确定性的 `clientSessionId`。腾讯插件本地变体已用回归测试确认同消息重放 ID 不变、同文本不同消息 ID 不同；真实 iLink 重放仍需端到端复核。
- OpenClaw 的入站 hook 和工具可能运行在不同插件实例；可信消息元数据因此通过本机短时 SQLite 表关联。查询键经 SHA-256 处理，记录十分钟过期，不把真实微信身份写入仓库。

## 分类和验收输入

分类源文件：config/expense-categories.json（11 个一级分类 / 45 个二级分类）。便于阅读的分类表：docs/expense-categories.md。

原始示例全部保留作为后续测试输入：

- 午饭12.8
- 晚饭16.8
- 橙汁2
- NTU衣服35
- 蜜雪冰城2.5
- 网线12.19
- 麦当劳15.7
- NTUC购物8.25
- NTUC购物8.25，买了两根芹菜，一个菜板

这些是回归样例，不应批量导入为真实支出。用户确认：在“食品酒水”下添加“饮料甜品”“超市购物”，不添加“生鲜食材”；分类已导入 Windows 账本并核验为 11/45。

## 下一阶段

下一步实现结构化微信确认回执：模型只负责金额、分类和备注语义；工具负责真实账本名、写入金额、分类、可信新加坡时间和固定排版。随后用新微信消息核对回复与 ezBookkeeping 记录。家庭网页查看属于独立后续阶段，需要先设计安全同步、登录、授权、备份和审计，不直接把本地账本暴露到公网。
